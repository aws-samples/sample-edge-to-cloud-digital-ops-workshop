## NOV's Current IoT Architecture (Max Edge)

- ~1,000 connected devices (rig and frac data vans), forecast to double annually
- Edge hardware: Raspberry Pi, Moxa boxes, small servers (~16GB); running Debian
- Per-device stack: `edged` daemon + Docker Compose → 3-container app (message bus, I/O gateway, `system config` API)
- Two data planes: **telemetry** (MQTT → IoT Core → Kinesis/MSK) and **control plane** (MQTT → `edged` → `system config`)
- **Security model: outbound-only.** No static inbound ports, no static edge IPs. All comms initiated by edge device. mTLS (moving from Auth0). IPv4/IPv6 iptables-managed firewall. This is non-negotiable.
- Current Day-1 provisioning: [Ansible](https://docs.ansible.com/) — works well for fresh imaging but can't reach devices post-deploy (conflicts with outbound-only model)
- Current Day-2 "solution": home-grown batch tool calling the Edge Manager API through the existing control plane — described as a stopgap; mostly Bash-script driven

## The Core Problem Brady Wants to Solve

| Gap Today | Desired State |
|-----------|---------------|
| One device at a time via Edge Manager | Fleet-level operations on cohorts |
| Bash scripts, no idempotency/rollback | Declarative desired state + reconciliation |
| No device shadow or desired/reported state model | Device shadows tracking app version, config, health |
| No staged rollout or abort criteria | Safe, observable fleet-level rollouts |
| No fleet grouping or reporting | Fleet indexing by customer, site, app version, health |

**The question Brady wants answered:** Can AWS IoT Core provide a better Day-2 operating model while preserving the outbound-only, mTLS industrial edge security posture?

## Relevant AWS Services to Know Cold

| Service | Role in This Context |
|---------|---------------------|
| [AWS IoT Jobs](https://docs.aws.amazon.com/iot/latest/developerguide/iot-jobs.html) | Push update operations to devices; devices poll for pending jobs — outbound-only compatible |
| [AWS IoT Device Client](https://github.com/awslabs/aws-iot-device-client) | Open-source reference agent; handles Jobs, Shadows, Fleet Provisioning, Tunneling |
| [Device Shadows](https://docs.aws.amazon.com/iot/latest/developerguide/iot-device-shadows.html) | Desired/reported state reconciliation; ideal for tracking app version, config, health |
| [Fleet Indexing](https://docs.aws.amazon.com/iot/latest/developerguide/iot-indexing.html) | Query and group devices by thing attributes, shadow state, connectivity status |
| [Thing Groups](https://docs.aws.amazon.com/iot/latest/developerguide/thing-groups.html) | Static + dynamic grouping; target for Job deployment cohorts |
| [Fleet Provisioning](https://docs.aws.amazon.com/iot/latest/developerguide/provision-wo-cert.html) | Zero-touch certificate provisioning by claim — relevant for Ansible Day-1 pain |
| [IoT Core MQTT broker](https://docs.aws.amazon.com/iot/latest/developerguide/mqtt.html) | Brady also asked about this as broker replacement at QBR — separate thread |

**Key insight for this architecture:** [AWS IoT Jobs uses a pull model](https://docs.aws.amazon.com/iot/latest/developerguide/jobs-devices.html) — the device polls `$aws/things/{thingName}/jobs/notify` for pending jobs. This is fully compatible with NOV's outbound-only security model. No inbound ports needed.

### Frame the architecture answer early
The good news: **AWS IoT Jobs is outbound-only by design.** Devices poll for pending jobs over the same MQTT/mTLS connection they already use for telemetry — no firewall changes required. This directly addresses the Ansible Day-2 problem.

Device Shadows add desired/reported state on top of that — so you can declare "target app version: 2.3.1" and let each device reconcile and report back independently.

### Set scope boundaries
The one-pager is ambitious (full fleet management platform). For the workshop, anchor on the two most valuable, most achievable items:
1. **IoT Jobs + staged rollout** for a Max Edge app update — this is the direct replacement for the batch tool
2. **Device Shadows for desired/reported state** — app version, config version, health status

Fleet indexing/grouping and the broader Edge Manager integration are the "future state" track — good to discuss but not workshop deliverables.
